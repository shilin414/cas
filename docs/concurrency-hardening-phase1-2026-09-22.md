## 变更与行为

### 1. 调度扫描公平性（R1）
- 到期计划扫描在 LIMIT 之前排除已有 active occurrence 的 queue 计划，skip 计划仍可推进。
- pending 准入先过滤 queued/running 冲突，再保证每个计划只选择最早的 pending。
- 已用尽用户 outstanding 配额的 pending 不占满扫描批次，其他用户仍能被选中。
- 最终准入仍在计划行锁内复核；没有为了性能取消幂等或重叠保护。

### 2. 用户配额统一（R4）
- 交互提交与定时 Run 创建共用用户行锁与 outstanding 检查。
- 准入事务显式 READ COMMITTED：拿到用户锁后使用每语句的新快照计数，不通过锁整个 runs 范围制造跨用户空隙锁冲突。
- 定时额度不足保留 pending occurrence 和投递目标快照，不创建多余会话、不消耗执行机会。pending 恢复准入时重新检查执行窗口和超时跳过策略。
- 一次性或已耗尽触发器，在等待额度时不会提前停用；其他推进分支也会保护已经接受的 pending；pending 被准入、跳过或判定不可执行后，没有后续触发/等待条目才自动关闭计划。
- 提示：该额度仍是未完成任务总量，包含等待输入/等待外部结果等未终结状态；不是“仅 CPU 正在执行”的计数。

### 3. Provider 策略失效时关闭准入（R2）
- 启动时无法读取权威策略、策略不存在或额度非正数，构建失败，不回退到更大的环境默认值。
- 生产装配的 ProviderSlots 在每次准入事务内读取并锁定数据库额度，不再只依赖进程启动快照。
- AILY_MAX_INFLIGHT 配置保留兼容解析，但不再作为生产执行额度的兜底或覆盖。
- 动态下调只阻止新准入；不会强杀已运行任务。应等待现存占用自然降到新上限。

### 4. 统一执行池与独立维护（R3）
- 正常消费、Redis reclaim、数据库补扫共享同一组本机执行许可，必须先获得许可再 claim。
- 补扫只在存在空闲许可时派发，仍在 MySQL 执行最终 claim CAS。
- 过期租约、parked 上游请求、过期 slot 清理由独立维护循环处理，不等待业务 handler 或执行池空位。
- 执行 Worker 的数据库扫描、准入和维护步骤增加有界操作超时。
- 停机时补扫启动的执行协程会被等待回收，不留后台游离执行。

### 5. 独立租约看门狗（R7）
- 每个执行有独立定时器；数据库续租不返回时，也会在租约的安全期限前取消本地执行。
- 心跳使用短超时与最多 4 个并行续租请求，避免一个慢任务阻塞全部续租。
- 已经过期的本地执行不再继续续租；晚到的成功心跳不能复活它。
- 本地注册拒绝旧 epoch 和重复 epoch，防止迟到的旧执行取消或覆盖新执行。
- 看门狗不直接提前释放可能仍在结束中的外部容量；仍由现有 fencing、handler 清理和外部状态协调负责。
- 限制：取消本地 context 不等于已经取消远端任务；不承诺上游服务任意失联情况下的外部 exactly-once。

### 6. 投递抢占与结果隔离（R5、R6）
- claim 原子条件同时检查 pending、预期 attempt、重试到期时间和 max_attempts。
- attempt 作为现有的单调递增执行代次；finish/requeue 也必须匹配该代次，旧发送者不能覆盖新发送者。
- 发送流程的 45 秒预算覆盖读取、claim、限流等待、身份获取与网络发送；小于 60 秒回收期限。
- 发送结束后使用独立且最多 5 秒的上下文写回，避免停机/超时直接丢失结果落库机会。
- 飞书适配器要求 UUID 发送接口，真正传递稳定的 IdempotencyKey，而不是仅在内部结构保存。
- 陈旧代次未更新到记录时，不计为本次成功/重试，避免误报指标。
- 限制：上游幂等窗口、异常网络与远端已接受但本地未知仍需真实故障验收；不可把 UUID 字段接通说成无限期 exactly-once。

### 7. 容量等待保留业务优先级（R8 部分）
- 容量不足/容量存储暂不可用采用 defer，而不是业务失败 retry，保留原交互/定时优先级。
- 本批尚未改变 1 秒等待重试间隔，也未彻底调整 started 事件时机或实现释放容量通知；写放大优化仍在第二阶段。

## 数据库与部署兼容性

- **没有新增 schema 迁移。**SQL 查询已由仓库现有 sqlc 重新生成，没有手改生成器输出。
- 依赖既有迁移中的用户状态与 occurrence 状态索引，仍需在隔离 MySQL 上检查实际执行计划。
- 旧版本 Worker 不具备本批所有保护。不能混跑部分新旧进程后就宣称全平台约束生效。
- 建议在正式发布前安排安全排空/维护窗口，按一致版本更新 API、Scheduler、执行 Worker、投递 Worker；先检查 providers.max_inflight 均为合理正值。
- 不建议只调大 WORKER_CONCURRENCY 或临时修改 AILY_MAX_INFLIGHT 来绕过策略启动错误。
- READ COMMITTED 准入与 Provider 策略热读取必须在目标 MySQL 版本下验收；不要直接对共享 dev/test 做故障注入。

## 回归测试覆盖

新增加/补强的测试包含：
- 前 100 个 queue 计划被阻塞时，后面的计划仍可被选中。
- pending 扫描按计划 FIFO，且用户满额不阻塞其他用户。
- managed Provider 策略不可读/缺失/为零不放行；数据库额度从 20 改为 2 后下一次准入立即采用新值，而非启动默认 100。
- 本机共享许可上限、取消等待、满池时维护仍可运行。
- 无心跳返回时独立到期取消、续租后重置期限、过期后不再续租、迟到旧 epoch 不覆盖新 epoch。
- 用户额度达到上限时不创建会话；准入使用 READ COMMITTED；一次性任务等待额度不被提前停用。
- 投递旧唤醒不发送、未来重试时间不抢占、旧 attempt 完成/重试不能写新代次、发送适配器传递真实 UUID。

`tests/integration/concurrency_hardening_test.go` 增加了 MySQL 专用回归：使用同一连接的临时表遮蔽业务表，不启动业务执行器。它们受 STUDIO_TEST_DB 开关控制，本机本轮未开启。

离线 SQL 验证另外对仓库原查询做了 11 项内存 SQLite 断言。它只验证筛选与更新条件，不代替 MySQL 行锁/隔离级别和跨进程压测。

## 验证结果

- 独立 Go 复审进行了三轮，发现的旧 epoch 注册、范围锁与耗尽计划收尾问题均补回归并整改；最后一轮在限定变更范围未发现剩余高/中风险问题。
- 原 SQL 在内存 SQLite 的 11 项筛选/更新断言通过；并非真实 MySQL 并发测试。
- 执行包离线语句覆盖率为 **21.2%**，大量持久化分支依赖本轮关闭的真实数据库测试；**没有达到 80% 包覆盖率，不将其标成覆盖率达标**。
- CGO_ENABLED=0 且没有可用 gcc，未运行 race detector；未安装 staticcheck。
