# 智能体协作流程：产品与交互设计提案

日期：2026-09-20  
状态：待确认的设计提案；不是已实现功能。本文不修改业务代码、不调用智能体、不发送飞书消息。  
工作名称：协作流程（Workflow）。

## 1. 结论

不要把它仅做成“复杂定时任务”，也不要把对话变成几名机器人轮流刷屏。

建议：**流程是可复用能力，自动化负责触发，对话负责使用和跟进，任务负责承载执行与成果。**

- 智能体：谁来做，负责某一项能力。
- 协作流程：如何配合、交接什么、何时审核与停止。
- 自动化：何时运行、用什么输入运行、是否启用。
- 任务：这一次运行的状态、成果、人工决定与消息投递结果。
- 飞书：显式的输出渠道；不是智能体之间的信息总线。

一条流程可被手动使用、对话中调用、按计划执行；不要分别存成三套流程。

## 3. 信息架构：一个定义，三个入口

### 主入口：自动化 → 协作流程

自动化页面建议有三个页签：

1. **自动任务**：当前定时任务的进化；展示何时执行、执行哪个能力、最近结果。
2. **协作流程**：创建、调试、发布和复用流程；不要求绑定定时器。
3. **运行记录**：跨自动化来源的运行视图；链接回同一个任务，避免重复记录。

从自动化卡片进入是“配置触发”，从流程卡片进入是“编辑协作方式”。同一流程可有多个自动任务，但每个任务有自己的计划、输入和经授权的投递参数。

### 高频入口：对话中的能力选择器

能力选择器增加“协作流程”。选中后，输入框显示当前流程名称与参与智能体，不改变普通 @ 文本的既有语义。

用户输入“分析本周销售并准备简报”后，先出现一张执行计划卡。首次启用外部消息发送时，必须看见目标与预览并确认；已经明确授权的自动任务可以按发布配置自动发送。

### 临时入口：把当前结果交给另一个智能体

某条成果的“交给其他智能体”打开接续面板：选择 B、写处理要求、勾选传入内容。可继续交给 A/C，也可“保存为协作流程”。保存前将本次私有内容替换为输入字段，并重新确认收件人配置，避免把临时数据写入共享模板。

先让用户快速完成一次协作，再引导他保存与定时化，而非一开始就面对空白画布。

## 4. 核心编排方式：有边界的协作，不是无限群聊

### 默认范式：生成 → 评审 → 修订 → 定稿

示例：

输入任务 → A 数据分析 → B 质量审核

- B 通过 → C 生成管理简报 → 保存成果 → 可选人工确认 → 可选飞书发送。
- B 退回且未超修订次数 → A 根据明确问题修订 → B 再次审核。
- 修订达到上限、输出无法识别或执行预算不足 → 等待人工处理，不自动发送不合格内容。

建议默认“最多修订 2 次”：含首次提交，最多审核 3 次。UI 写明这个含义，避免“2 轮”到底算什么的歧义。

第一版允许顺序、条件分支、受限返工；不允许任意循环连线。返工用专门的“评审与修订”结构，有明确出口、计数和预算。

### 不同智能体如何拿到信息

默认不是把整个历史聊天复制过去。每一步显式配置：

- 原始需求；
- 指定上游步骤的最终结果或摘要；
- 明确选择的文件/成果引用；
- 当前评审意见、轮次；
- 本步骤自己的处理要求。

输入由可点选的变量片段组成，如“原始任务”“A 的最终分析”“B 的修订建议”；高级模式才显示内部路径。点击片段可追溯到原文。

A 再次执行时默认继承本次流程自己的工作上下文，不读取该用户在 A 上的其他私人会话。必要时为一个流程实例内的每个智能体建立独立的上下文容器，供返工续用。

### 审核输出

对用户展示“通过 / 需要修改 / 无法判断”。内部要求机器可验证的结构化结果，例如 decision、issues、revision_request。

自然语言“总体还不错”不能直接当作通过。提供商若不能稳定返回结构化字段，需增加受约束解析及校验；解析失败进入人工处理，不能自动放行。

## 5. 编辑体验：步骤视图优先，画布视图进阶

两种视图编辑同一份流程定义，不维护两套逻辑。

### 步骤视图（默认）

从上到下：输入任务 → A → 评审与修订 → C → 成果 → 飞书。每一步显示角色、输入来源、输出、分支条件。

优点：用户不需要学习拖线；窄屏和移动端也能读；串联和评审循环更清晰。

### 画布视图（高级）

中央有自动布局的节点和方向线；选中节点，右侧显示设置。新增节点从接续位置添加，自动连接合法上游。不默认提供任意脚本节点或无限自由画布。

编辑页局部页头（非全局 Header）：流程名称、草稿/已发布版本、步骤/画布切换、试运行、发布。

右侧设置分成三组：

- 职责：智能体、处理要求、输出格式。
- 信息：传入哪些内容、引用哪些成果。
- 控制：失败怎么办、超时、修订限制、是否等待人工。

### 节点范围

首版：任务输入、智能体执行、条件路由、评审修订结构、人工确认、保存成果、飞书通知、结束。

后续：并行处理/汇总、子流程、事件触发、允许列表内的工具节点。不要首版做一个任意脚本自动化平台。

### 从自然语言建流程

可用一句话“先让 A 分析，B 审核，不通过退回，最后 C 整理并通知群组”生成草稿。

模型只能生成候选配置，不可直接发布、选定陌生收件人或启动付费调用。系统需要检查智能体可用性、分支出口、变量引用、权限与循环上限。此能力适合后续增强，首版从模板开始即可。

## 6. 对话中的运行体验

不要为每一个内部步骤插入一条巨大的聊天消息。

### 执行中：一张持续更新的协作卡

显示流程名、来源（手动/自动）、版本、当前步骤、已完成步骤、轮次和暂停/取消入口。进度以已完成的实际步骤为主，动态返工时不伪造一个永不回退的精确百分比。

卡片示例：

本周销售复盘 · 协作中

A 已完成分析 → B 要求修订 → A 第 1 次修订中

“审核发现两处口径不一致”

展开协作过程 / 取消本次运行

这里的过程是可审计的输入输出、工具动作摘要、评审依据，不是模型隐藏思维链。

### 人工介入：在同一任务继续

当 B 无法判断、循环到上限或需要外发确认，出现行动卡：查看成果、补充要求、继续修订、明确采用当前版本、取消。

在流程运行时用户输入补充信息，必须选择“下个安全点生效”或“停止后重跑”，不能悄悄改掉正在执行的输入。人工改动有来源、时间和版本记录。

### 完成：成果优先，过程折叠

默认展示最终简报或成果卡，不将 A/B/C 的全文全部铺开。下方展示协作轨迹和独立的投递状态：

“成果已生成 · 飞书 1/2 个目标已送达，1 个发送失败”

失败按钮是“重试未送达目标”，而不是重新执行 A/B/C。

### 与任务列表关系

一次流程运行对应一个可追踪任务/任务活动。内部节点运行聚合在流程轨迹里，不污染最近任务列表；手动对话调用沿用当前任务，计划触发默认新建任务。两种来源最终都定位到同一个运行详情组件。

## 7. 飞书设计：显式、可预览、能追踪

提供三种易懂选项：不发送、确认后发送、按已授权配置自动发送。

收件人使用现有用户/群组选择体验；第一版只用明确选择的目标，不让模型根据文本随意猜人或群。保存名称用于展示，实际发送用稳定 ID 并重新验证权限。

建议首版默认只在最终成果通过审核后发送；中途通知、失败告警作为高级选项。评审循环中的通知默认按本次运行去重，不每次返工都刷群。

消息预览展示标题、摘要、成果入口、目标、发送身份与发送时间条件。发送正文与可访问链接分开检查权限：发送成功不等于接收人有权打开成果；不得自动把私有任务改成公开分享。

首版可复用现有摘要能力；富文本飞书卡片、逐字全文和交互按钮需要单独验证提供商接口，不能仅因原对话转发已有卡片就宣称流程天然支持。

外发确认绑定成果快照/哈希和目标集合；审核后修改内容或收件人需要重新确认。自动任务的授权策略随发布版本冻结，执行时仍复核用户、智能体、成果和目标的权限。

## 8. 高级感的来源

不是满屏发光连线，而是信息层级、平静的运行反馈与可控性。

- 延续 小安工作助手 的工作台布局和主题；中性表面、低对比边界，蓝色用于当前选中和主操作。
- 流程节点以角色、明确动词和输入输出表达，不用抽象“LLM 01”。
- 保留现有智能体头像；只给当前执行、等待人工和失败状态明显强调。
- 普通用户先看到任务目标与成果，专业用户展开节点轨迹和字段映射。
- 自动布局、少量状态过渡；不做循环闪烁的“忙碌动画”；遵守减少动态效果设置。
- 所有关键状态有文字，不依赖颜色；键盘可操作。
- 移动端默认步骤轨迹；复杂画布编辑留在桌面端，手机仍能查看、确认、取消和重试投递。

## 9. 实现契约（建议，需架构评审）

### 新增逻辑对象

- Workflow：流程身份、名称、拥有者、可见范围。
- WorkflowVersion：不可变节点、路由、字段引用、输出契约与安全策略快照。
- WorkflowExecution：一次流程运行；关联当前 Task/Conversation、版本、触发来源、实际输入。
- WorkflowStepExecution：一次节点访问；node_id + visit_index + attempt 区分返工和失败重试。调用智能体时关联既有 Run。
- ApprovalRequest：人工决定、批准人、绑定的成果与目标快照、过期时间。
- DeliveryExecution：继续承载外部发送，增加对流程/节点/成果来源的显式关联。

以上是逻辑模型，不是已批准的数据库迁移表名。

Schedule 触发目标扩展为受校验的 application 或 workflow_version 引用，旧 application_id 兼容保留；不要把两者伪装为同一数值 ID。触发记录也需能引用 WorkflowExecution，而不是强行让多步骤只对应一条 Run。

### 状态

- 流程版本：草稿 → 已发布 → 停用；编辑已发布流程产生新版本。
- 执行：待启动 → 排队 → 运行 → 等待人工/暂停 → 继续 → 成功/失败/取消。
- 节点：待就绪、就绪、排队、执行中、成功、失败、跳过、取消。
- 投递：独立维护待发、发送中、已送达、失败及结果未知等状态语义。

暂停在安全边界生效：当前在途执行可能完成，但暂停后不可调度后续节点。取消是尽力停止在途请求，不能撤销已经发生的上游计费或已发飞书消息。

### 必须保持的不变量

1. 每个执行固定流程版本和输入快照；编辑定义不改变运行中的实例。
2. 后续节点只消费持久化、权威终态结果，不以流式文本结束作为成功判据。
3. 单次智能体执行继续经过既有准入、配额、Run 状态机和 Worker；编排只是协调层。
4. 节点访问/重试、调度命令有幂等键；事务中记录状态推进与 Outbox，断线或进程崩溃后可恢复。
5. 用户关页不停止流程，SSE 只负责观察；先实现持久状态推进，不在前端串 HTTP 请求。
6. 最大修订次数、全流程截止时间、最大节点访问数和模型调用预算均受服务端约束；预算不可只放 UI。
7. 身份使用明确的执行人/授权上下文，不借作者凭证提升调用者权限；执行前和外发前重新校验。
8. 投递失败不重做已成功的模型节点；每目标跟踪结果，稳定投递键去重。外部请求超时存在结果未知窗口，不能宣称 CAS 可保证外部绝对仅发送一次；需验证渠道幂等能力并保守处理不明结果。
9. 恢复人工确认使用原状态；改输入重跑属于新 attempt/分支，并使相关下游结果与授权失效，历史保留可追溯。
10. 日志展示执行事件和交接依据，不记录或暴露未授权私密上下文；共享模板不包含临时个人会话内容。

### 安全试运行

UI 中“演示”不调用模型、不发消息。“试运行”如果调用真实模型，必须显示会消耗额度，并默认把所有外部发送替换为预览。此 dry-run 标记由后端执行，不能靠前端隐藏按钮实现。

### 待验证技术风险

- Aily 对每步骤上下文隔离、会话续用和稳定结构化输出的支持情况。
- 既有 DeliveryExecution 与 Schedule/Share 的具体耦合及流程来源迁移方案。
- 一个 Task 展示多个内部 Run 时，与 ChatRenderer、RunChatPanel、SSE 和历史回放的兼容。
- 当前运行权限模型能否安全表达共享流程的逐节点能力可见性。

## 10. 分阶段交付，不先做大而全

### 阶段一：把你描述的核心场景完整做通

- 步骤编辑器、少量模板；A → B → C 顺序链。
- B 通过/退回、返回 A 的有限修订、超限人工处理。
- 对话内一次性使用与任务轨迹；最终成果卡。
- 可选飞书用户/群组发送、预览/确认、逐目标结果与单独重试。
- 流程发布版本、停止/恢复边界、真实执行/投递测试。
- 既有自动化能够选择一个已发布流程。

### 阶段二：增强编辑和复用

- 高级画布、并行与汇总、输入字段编辑、流程模板库。
- 临时接续一键保存流程、自然语言生成草稿、运行版本比较。

### 阶段三：有限的动态调度

- 调度型智能体仅在允许的角色/工具内选择下一步。
- 加强预算、评估、审计和外发审批。
- 仍不做无边界“无限自主讨论”。

## 11. 核心验收用例

1. A 成功，B 通过，C 成功：只展示一个主任务，结果可追溯到每一步。
2. B 首次退回：A 能拿到 B 的明确问题、原始需求和上一稿，不读取其他会话。
3. 连续超过 2 次修订：第 3 次审核退回后等待人工，不继续循环、不发飞书。
4. B 输出无法解析：进入人工处理，不误当通过。
5. 节点排队时刷新/关页，worker 重启或重复消费事件：不会重复启动同一次逻辑节点。
6. A/B/C 已成功，飞书部分目标失败：仅重试未送达目标，模型节点不重跑。
7. 审批后改收件人或成果正文：旧审批失效。
8. 编辑并发布 v2 时，运行中的 v1 和已绑定 v1 的自动任务不被静默改写。
9. 执行中权限失效、达到调用预算、超时或取消：不会启动不应执行的后续节点。
10. 试运行所有外发路径都是预览；生产外发由后端策略约束。
11. 窄屏可阅读步骤、处理确认；颜色关闭和键盘导航仍能识别状态和完成操作。

## 12. 建议默认值及待确认点

建议默认：名称“协作流程”、挂在自动化下、可在对话能力选择器调用、步骤视图优先、最多修订 2 次、外发首次确认、定时任务绑定发布版本、新建任务承载每次计划执行。

待你确认的产品取舍：更偏“后台流程平台”还是“对话中的协作团队”？本提案推荐后者的使用体验，加上前者的可控执行机制，两者共用同一流程定义。

进入开发前需一次架构评审，把逻辑对象、Provider 输出契约、上下文隔离及调度/投递的扩展点落实。当前状态：可进入架构细化，不应把本提案当成已验证实现。
