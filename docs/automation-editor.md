# 自动化编辑器与推送条件

当前运行需要 Scheduler、执行 Worker、投递 Worker；数据库变更人工执行，见[数据库手册](deployment/database.md)。

## 产品范围

自动化沿用现有 Schedule → Occurrence → Run → DeliveryExecution 链路；“自动化”是用户界面的统一名称，不改变既有 `/api/v2/schedules` 接口和路由。

- PC：双栏编辑器，左侧标题、任务描述与执行智能体，右侧触发器、高级配置与推送配置，底部固定操作。
- 移动端：创建主页面、触发配置页面、推送配置页面；指定开始/结束时间在底部面板编辑，确认后回填。
- 支持现有单次、每天、每周、每月频率；保留时区、未来执行时间预览和既有执行策略。
- 推送目标使用现有飞书用户/群聊搜索与分页能力，不假设候选第一页就是全量。
- 截图只用于信息结构参考；不新增没有后端能力的项目、附件、闲时执行占位功能。

## 时间有效期

`trigger.starts_at` 与 `trigger.ends_at` 是可选 RFC3339 时间点。

- 不传 `starts_at`：立即生效。
- 不传 `ends_at`：永不结束。
- 指定日期输入按设备本地时区转成绝对时间；重复频率仍按自动化设置的时区解释。
- 开始/结束顺序必须合法；无效值必须提示，不能静默退回立即生效或永不结束。
- 预览与真实调度使用相同时间范围，不能只限制 UI。
- 编辑旧自动化时必须完整回填，切换为立即生效/永不结束时清除对应限制。

## 推送条件

每个目标携带 `condition`：

```json
{"operator":"contains","text":"需要关注"}
```

操作符：

| operator | 界面含义 |
| --- | --- |
| `always` | 始终推送 |
| `contains` | 回复包含指定文本时推送 |
| `not_contains` | 回复不包含指定文本时推送 |

- 使用最终助手回复做大小写敏感的字面包含判断，不是正则，也不是让模型解释自然语言条件。
- 非 `always` 必须配置有效文本；旧配置缺少条件时保持始终推送。
- 条件不匹配只跳过推送，不能将已成功的智能体执行改成失败。
- 在创建执行批次时保存投递条件快照，后续编辑自动化不应改变已在途执行的推送规则。
- 验证使用测试接收目标与拦截的浏览器请求，不向真实用户/群组发送测试消息。

## 执行边界与发布要求

起止端点包含在有效期内；手动立即执行也必须在有效期内，否则返回 409。已经进入执行中的任务不会在结束时间到达时被中断。耗尽有效期的自动化会停用。时间精度最多支持毫秒，与 MySQL DATETIME(3) 一致，拒绝更高精度以避免数据库舍入后越界。

发布时先应用 0040_automation_windows_conditions，再同步升级 API、调度器和执行/投递消费者，避免新旧服务混跑绕过新规则。旧推送目标迁移后默认始终推送。
